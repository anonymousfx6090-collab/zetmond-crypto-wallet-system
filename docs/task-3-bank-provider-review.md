## Recommendation and evidence limits

Implement the selected **Paystack** integration against its actual ownership contract. Its [official OpenAPI specification at `07c5abc`](https://github.com/PaystackOSS/openapi/tree/07c5abc8c34536e98a7755a5338178b4f430b09b) documents Nigerian bank listing, account-name resolution and a separate customer-identification request. The new read-only server client implements the first two operations. The customer-identification endpoint's HTTP 202 response is acceptance only; its authenticated final result, exact account/identity binding, recovery rules and account eligibility still need confirmation before adapter activation. The owner has not yet created a Paystack account.

**Historical alternatives:** Monnify's vendor-published SDK/tool definitions establish specific Nigerian bank-name and BVN/account-match operations; see the [Monnify evaluation](task-3-monnify-review.md) for the endpoint-version discrepancy and sandbox gaps. Mono's Connect SDK documents bank linking and Account Match. These remain research alternatives, not the current selection or evidence of crypto-business eligibility.

The customer's browser must not send banking passwords to Zetmond. The provider's window handles connection, and the backend must independently exchange the returned code and fetch the authoritative account/identity. Browser success or `check_account_match: true` alone cannot mark a destination verified. A plain bank-account-name lookup is insufficient proof of control.

The Paystack website documentation was blocked by the current network policy. Its public official GitHub OpenAPI source was accessible and was statically inspected; a [pinned extract](contracts/paystack-bank-lookups.openapi.json) retains the vendor contract. Earlier research below uses public SDK archives published on npm, with their registry integrity hashes checked before static inspection. No vendor code was executed, added as a dependency, or called with credentials. Published contracts and types do not replace a provider agreement or account-backed sandbox evidence.

## Working bank flow

Keep destination records and ownership checks provider-neutral while implementing Paystack for Nigeria. Existing account-number forms and safeguards supply the destination-detail step. The new server client can list Nigerian banks and resolve account names, and `paystack:check` reports catalogue metadata only. It is deliberately absent from the approval-provider registry: neither a name lookup nor browser authorization establishes ownership. The complete flow still needs the authenticated identification result contract, supported account features and a configured account.

## Implemented ownership checks

Migration `006_bank_ownership_policy.sql` adds destination-owned `provider_policy_version` and `name_match_policy` pins and a separate `under_review` status. New intents record both policies from server configuration. Existing rows have null pins; they are retained but cannot be used or silently assigned a new verification policy.

The worker still requires independently authenticated ownership evidence, current customer/market/mode, destination fingerprint, identity-attempt binding, explicit provider ownership/match flags and the exact pinned provider policy. It then independently compares the returned holder name with the encrypted current KYC name. Local `zetmond-exact-name-v1` accepts only casing, spacing and Unicode NFC equivalence. Missing, different, partial, reordered, company, transliterated, punctuation-altered or control-character names are held for review. This comparison only restricts a provider decision; it never proves account control or replaces a vendor's ownership check.

Name conflicts retain minimal encrypted evidence and their provider revision. A newer authenticated provider result is checked again; review does not become a permanent mismatch. Public listings and audit metadata do not reveal holder names or full account numbers. Provider/local policy changes hold work before an external request, retain the original pins, and record one local audit event without inventing a provider revision. Such a destination needs fresh verification under the current policy rather than an automatic retry.

The provider-neutral renewal flow now prepares an opaque operation digest from the server's saved bank, current KYC attempt/revision, provider/mode and policy versions. Fresh `bank_reverify` MFA authorizes that exact intent. Creation of the successor, consumption of the grant, inactivation of the already-outdated source and job enqueue commit together. Migration `008_bank_reverification.sql` preserves the original encrypted details/evidence and decision history, links the successor, pins its KYC revision, and permits only one current destination for the same account. A changed or missing KYC revision prevents usability and provider work until freshly verified; historical pins are not inferred. Same-operation recovery returns the existing intent; competing renewals cannot create two successors. Current usable records and unrelated banks cannot be retired through this route. Provider-backed acceptance and manual retirement/exception policies remain outstanding.

Listings require a current approved identity with evidence, matching country/mode and both current policies before a destination is usable. They expose a safe renewal flag and an accessible ownership status. The customer sees review/renewal information and cannot request a status retry for an outdated policy. The owner still needs to approve final production matching/exception rules; no provider has been enabled by this prepared conservative guard.

## Implementation handoff

Existing code already supplies owner-scoped bank records, exact-operation MFA, encrypted account details, masked display, immutable identity/policy binding and durable jobs. Keep these protections when adding the selected provider. Do not replace them with a client-supplied owner name or `nameMatch=true`.

1. Confirm the provider supports Zetmond's disclosed custodial crypto/P2P business and each required country, bank, currency and account type. Record actual sandbox access and fees without inventing a price or free tier. Bank verification is separate from fiat collection/payout approval.
2. Use the pinned Paystack bank catalogue and name-resolution contracts, then obtain the current customer-identification final-result, canonical recovery and webhook contracts. Confirm server-owned customer, operation and exact account binding. Hosted connection/code exchange is relevant only if that flow is documented and selected; it is not assumed to be Paystack's API.
3. Keep private API credentials server-side. Record a durable intent before starting a potentially chargeable operation; persist the linked provider account and uncertain outcomes before retrying. Never log browser authorization codes, bank credentials or unmasked account data.
4. Bind each result to the current customer, market, bank/account fingerprint, current Smile ID identity attempt and chosen matching policy. Server-side identity/account evidence must be checked independently; a resolved name, generic customer flag or accepted identification request cannot verify a destination.
5. Retain the prepared conservative name guard and immutable policy pins. Confirm production matching/exception and retirement/reverification procedures against the actual provider contract before activation. Do not infer a fuzzy threshold, strip meaningful characters, or accept a typed name as ownership evidence.
6. Preserve KYC, verified email, fresh exact-operation authenticator approval and staging financial denial. Bank-connection consent is an additional acknowledgement, not a replacement for account authorization.
7. Demonstrate supported sandbox happy path, wrong account, name mismatch, interrupted connection, stale/duplicate callback, code reuse, revoked access, API restart and unsupported-country behavior for each enabled market. Evidence must include authoritative server results, not screenshots or simulated approvals.

The unresolved vendor coverage, endpoint contract and account access prevent claiming a completed bank integration. Unsupported countries/banks continue to show unavailable instead of a fabricated approval.

## Validation of the prepared policy guard

The isolated API TypeScript build and customer production build passed. The full API run completed **146 checks: 145 passed, one optional Redis check skipped**. New cases cover current-policy pins, leading-zero account identifiers, independent holder-name comparison, contradictory provider match flags, encrypted review evidence, newer-result rechecking, outdated/unversioned records without provider calls, immutable provider revisions and rejection of client-supplied policy fields. Removing current KYC evidence also disables bank usability and new additions.

All **23 customer browser cases** passed across the full run and targeted rerun. The new case covers accessible review/renewal states and blocked outdated-policy retries. An existing admin MFA case crossed a 30-second TOTP boundary in the full run; its test now waits for a fresh interval before generating a code and passed on rerun. Production MFA validation was not changed. Browser provider responses remain labeled fixtures; no account-backed bank verification was performed.
